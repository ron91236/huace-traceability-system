# 溯源逻辑对比与改进建议

> 调研日期：2026-08-31 ｜ 范围：trace-system 溯源链路 vs 国家追溯平台/GS1 标准/一物一码 SaaS 实践

## 结论先行

本系统「码→商品→批次→企业→证书→检测报告」的主链路是**完整且闭环**的（`CodePackageItem` 同时挂 enterpriseId/goodsId/certId/batchId，基础信息与检测报告可展示），难点不在主链路，而在**生产/养殖加工/物流等中间过程数据整体缺失、溯源页信息无分层优先级、码编号缺乏 GS1 规则**。建议分短、中期补强。

## 一、现状梳理（代码事实）

- `TracePageService.queryBySerialNo` 先从 MongoDB 取码包明细（亿级码外部存储，回退 MySQL），再逐段拼装 `enterprise/goods/cert/batch/base/testReports/traceTemplate/customFields`，结果 `@Cacheable("tracePage")` 缓存。
- 检测报告已做多报告改造（`testReportService.buildReportListForBatch`），支持 PDF→图片。
- 防伪有「扫码即验」与「输码验」两套，含扫码计数与首扫预警雏形。
- **断点一**：`CodePackageItem.orderCodeId`（关联 `OrderCode`，含 `productionTime` 生产时间）在溯源结果中**未返回、未查询**，生产时间字段虽存在却未对 C 端暴露。
- **断点二**：前端 `section-fields.ts` 已定义 `breed-archive/farm-info/transport-info/slaughter-info/cutting-record` 等模块（养殖档案、调运、屠宰、分割），但后端**没有对应实体，也从不返回这些数据**——这些模块渲染时永远为空，属「有 UI 无数据」的死模块。
- **断点三**：`ScanRecord` 有 province/city 字段但**从未写入 IP 归属地**，无法做窜货/地域分析。

## 二、行业对照（依据）

1. **国家追溯平台/标准**：NY/T 4712-2025 已规范化追溯数据格式，国家平台推「一张网」、部省数据标准化，核心数据项围绕**主体、产品、生产（种养殖/加工）、检测、流通**五类，强调生产加工记录与检验检测报告的强制采集与可核验。
2. **GS1 标准**：GTIN（商品）+ 批次号（Lot）+ 序列号（Serial）三层编码，通过应用标识符 AI(01)/(10)/(21) 分层，「标识标准化 → 数据关联 → 事件记录」，支撑从单品到物流单元的统一追溯。
3. **一物一码 SaaS 实践**：成熟方案（阿里满天星/甲骨文超级码/和码等）溯源页普遍采用「**防伪结论置顶 → 关键节点时间轴（生产/质检/物流）→ 证书检测详情 → 企业品牌**」的信息层级，并强调一物一码 + 序列化防窜货。

## 三、改进建议清单

### A. 码设计（中期）
- **依据**：GS1 三层编码。**现状**：`serialNo` 无规范规则，防伪码与流水号分离但无 GTIN/批次关联展示。
- **改法**：在码生成阶段引入 `GTIN + 批号(AI10) + 序列号(AI21)` 结构，`serialNo` 规范化为可校验长度/校验位；明确「一物一码」（单包装）与「一物多码」（外包装+内码关联）场景，外码挂批次、内码挂单品。
- **改造量**：中（涉及码包生成、绑定逻辑与前端展示）。

### B. 溯源页信息分层（短期，推荐优先）
- **依据**：行业「防伪结论置顶」体验；**现状**：默认 `defaultSections` 把企业/商品排在检测与防伪之前，防伪结论不显眼。
- **改法**：模板默认顺序调整为「防伪/首扫结论 → 检测报告结论 → 产品+批次 → 基地/企业详情 → 证书」；在 `TraceView.vue` 顶部加统一「真实性结论条」（正品·已查验 N 次·生产时间）。
- **改造量**：小（纯前端模板顺序 + 一个结论组件）。

### C. 补齐生产/加工/物流数据链路（中期，3–6 月）
- **依据**：国家平台与 NY/T 4712 要求生产加工记录可追溯；**现状**：`transport/slaughter/cutting/breed` 全部缺失。
- **改法**：新增 `productionRecord`(播种/投料/用药)、`processRecord`(加工/屠宰/分割)、`logisticsNode`(装车/到货/温控) 实体与录入接口，按批次关联；在 `TracePageService` 返回并按时间轴输出，活化现有死模块。
- **改造量**：大（多个实体+管理端录入页+C端时间轴）。

### D. 断点快速修复（短期，改造量小）
1. 返回 `OrderCode.productionTime` 及订单号，补上「生产时间」这一关键节点（`OrderCode` 已有该字段，仅差暴露）。
2. `ScanRecord` 落库时接入 IP 库补 province/city，支撑防窜货分析（字段已预留）。
3. 清理 `section-fields.ts` 中无数据支撑的死模块，避免用户扫码看到空模块。

### 总体优先级

**先做 B + D（小改造、体验立竿见影），再做 C（补齐过程数据）、A（码规范化）。**
